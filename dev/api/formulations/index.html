Core: Formulations, Units and Registry (PowerfulCore)

Formulation and data format traits, per-unit kinds, bus type codes, the solution interface and the model registry. These names are defined in PowerfulCore.Foundation (or PowerfulCore itself) and exported by PowerfulCore.

Formulations

PowerfulCore.Foundation.DEFAULT_FORMULATION — Constant
DEFAULT_FORMULATION

The formulation used when none is specified: PowerInjection().

source
PowerfulCore.Foundation.CurrentInjection — Type
CurrentInjection <: FormulationTrait

Current injection formulation (alternative, better numerics).

Variables

  • Rectangular coordinates: (Vr, Vi) - real and imaginary voltage

Residuals

  • Current balance at each bus: Ir = 0, Ii = 0
  • Branch contributes: Iri, Iii, Irj, Iij (current flows)
  • Load contributes: Ir, Ii (consumption as current)
  • Generator contributes: Ir (from P), Vmag (control)

Characteristics

  • Better numerical properties for ill-conditioned systems
  • No trigonometric functions in Jacobian (algebraic only)
  • Natural for rectangular voltage coordinates
  • I = Y*V is linear in V (rectangular)

Benefits

  • Better convergence near voltage collapse
  • Simpler derivatives (no sin/cos)
  • Can leverage Y-bus sparsity more directly
source
PowerfulCore.Foundation.DCPowerFlow — Type
DCPowerFlow <: FormulationTrait

DC power flow formulation (linearized approximation).

Variables

  • Voltage angles only: θ - no voltage magnitudes
  • All voltage magnitudes assumed at 1.0 pu

Residuals

  • Active power balance only: P = 0
  • Reactive power ignored (Q equations removed)
  • Branch contributes: Pi, Pj (active power flows only)
  • Load contributes: P (active consumption only)
  • Generator contributes: P (active injection only)

Characteristics

  • Linear equations: P = B'θ where B' is the DC admittance matrix
  • Fast solution via direct linear solve
  • No convergence issues (linear system always solvable if connected)
  • Commonly used for contingency analysis and economic dispatch

Assumptions

  • All voltage magnitudes = 1.0 pu
  • Small angle differences: sin(θi - θj) ≈ θi - θj
  • Branch resistance negligible: r << x
  • Reactive power negligible: Pij ≈ (θi - θ_j) / x

Benefits

  • Extremely fast (linear solve, no iteration needed)
  • Guaranteed convergence for connected networks
  • Good approximation for transmission networks with high X/R ratio
  • Industry standard for planning and market applications

Limitations

  • Ignores voltage magnitude variations
  • Ignores reactive power flows
  • Less accurate for distribution networks (low X/R)
  • Cannot capture voltage collapse phenomena

PowerfulCore.Foundation.FormulationTrait — Type
FormulationTrait

Abstract base for power flow equation formulations.

Formulations determine the mathematical representation of network equations:

  • PowerInjection: Power balance equations S = P + jQ (default, nonlinear)
  • CurrentInjection: Current balance equations I = Ir + j*Ii (nonlinear)
  • DCPowerFlow: Active power balance P = 0 only (linear approximation)

The formulation affects:

  1. What equations are solved (residuals)
  2. What variables are used (polar vs rectangular vs angles-only)
  3. How kernels compute contributions (nonlinear vs linear)
  4. Solver selection (Newton vs direct linear solve)
source
PowerfulCore.Foundation.PowerInjection — Type
PowerInjection <: FormulationTrait

Power injection formulation (default, existing implementation).

Variables

  • Polar coordinates: (θ, V) - angle and magnitude

Residuals

  • Power balance at each bus: P = 0, Q = 0
  • Branch contributes: Pi, Qi, Pj, Qj (power flows)
  • Load contributes: P, Q (consumption)
  • Generator contributes: P (injection), V_setpoint (control)

Characteristics

  • Most common formulation in power flow
  • Well-understood convergence properties
  • Trigonometric functions in Jacobian
source
PowerfulCore.Foundation.supports_formulation — Method
supports_formulation(::Type{M}, ::Type{F}) -> Bool where {M<:AbstractModel, F<:FormulationTrait}

Whether model type M is defined in formulation F.

By default this follows the model metadata, the definition of the model's variables and residuals: the base metadata is the PowerInjection form, and another formulation is supported when the model registers variables or residuals for it (vars_by_formulation / residuals_by_formulation). A model without variables or residuals (e.g. an area or zone) takes part in every formulation. Problem constructors check every model of the system with check_formulation_support.

Example

supports_formulation(Branch, CurrentInjection)  # true: Branch registers (v_r, v_i) metadata
supports_formulation(GENROU, CurrentInjection)  # false: defined in the PowerInjection form only

System Settings

PowerfulCore.Foundation.SystemConfig — Type
SystemConfig{T}

System-wide settings of a power system model, owned by its SystemModel (sys.settings) so that every analysis of the system uses the same values. Solver options live in SimConfig instead.

Type Parameter

  • T<:AbstractFloat: Float type matching simulation (Float64, Float32)

Fields

  • frequency_base::T: System frequency base in Hz (default: 60.0)
  • mva_base::T: System MVA base (default: 100.0)
  • omega_base::T: Angular frequency = 2pi * frequency_base (computed)
  • constant_power_vmin::T: Voltage (pu) below which constant-power load (PQ pl, ql) is reduced smoothly to zero at zero voltage (default: 0.7, the default of PSS/E PQBRAK and of PowerWorld's minimum voltage for constant power loads); see constant_power_factor

Example

sys = SystemModel(case)                                 # settings from the case (base MVA, frequency)
sys = SystemModel(case; frequency_base = 50.0)          # override
sys = SystemModel(case; constant_power_vmin = 0.8)      # constant-power breakpoint
sys.settings.omega_base

Solution Interface

PowerfulCore.Foundation.AbstractSteadyStateSolution — Type
AbstractSteadyStateSolution

Abstract type for steady-state solution results.

Packages that need steady-state solutions for initialization (e.g., TDS and any simulation mode built on it) should depend on this interface rather than concrete solution types.

Required Interface Methods

Implementations must provide:

  • get_system(sol) → SystemModel
  • get_address_manager(sol) → AddressManager
  • get_state_vector(sol) → AbstractVector{<:Real}
  • get_residual_norm(sol) → Real

Optional Interface Methods

  • is_converged(sol) → Bool (default: true)

Example Implementation

struct PowerFlowSolution <: AbstractSteadyStateSolution
    prob::ACPowerFlowProblem
    dae::DAE
    converged::Bool
    # ...
end

get_system(sol::PowerFlowSolution) = sol.prob.sys
get_address_manager(sol::PowerFlowSolution) = sol.prob.address_manager
get_state_vector(sol::PowerFlowSolution) = sol.dae.y
is_converged(sol::PowerFlowSolution) = sol.converged

Usage in TDS

function setup_tds(sol::AbstractSteadyStateSolution, dyn_models::NamedTuple; config)
    sys = get_system(sol)
    am = get_address_manager(sol)
    y = get_state_vector(sol)
    # ... use sys, am, y for initialization
end

PowerfulCore.register_pending_models! — Method
register_pending_models!(models)

Register a collection of model types to the shared MODEL_REGISTRY.

Called from sub-package __init__() functions to register models that were collected during precompilation. This is the standard pattern for cross-package model registration in Julia.

Example

# In sub-package module file:
const _PENDING_MODELS = Type[]

# ... includes with @register_model calls ...

function __init__()
    PowerfulCore.register_pending_models!(_PENDING_MODELS)
end
source
PowerfulCore.@init_model_registry — Macro
@init_model_registry

Initialize model registration infrastructure for a sub-package.

Call this macro once at the top of a sub-package module (after using PowerfulCore) to set up the _PENDING_MODELS vector and _EXPORTED_MODEL_NAMES for tracking. Then use @register_model in individual model files, and call register_pending_models!(_PENDING_MODELS) in __init__().

After all models are registered (after all includes), copy _EXPORTED_MODEL_NAMES to EXPORTED_MODELS for use by the umbrella package.

Example

module PowerfulPF
using PowerfulCore
@init_model_registry  # Creates _PENDING_MODELS and _EXPORTED_MODEL_NAMES

include("models/bus.jl")  # Contains @register_model Bus
include("models/pq.jl")   # Contains @register_model PQ

# After all includes, create EXPORTED_MODELS for umbrella package
const EXPORTED_MODELS = copy(_EXPORTED_MODEL_NAMES)

function __init__()
    register_pending_models!(_PENDING_MODELS)
end
end
source
PowerfulCore.@register_model — Macro

Macro to register a model type.

When called from a sub-package that defines _PENDING_MODELS::Vector{Type}, the model type is added to that vector during precompilation. The sub-package's __init__() should then call register_pending_models!(_PENDING_MODELS) to transfer them to the shared registry at runtime.

Also tracks the model name in _EXPORTED_MODEL_NAMES for automatic export by the umbrella package (Powerful.jl).

When called from PowerfulCore itself, directly updates MODEL_REGISTRY.
