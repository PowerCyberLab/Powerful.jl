Core: Metadata and Traits (PowerfulCore)

Model metadata, traits, groups and base quantities. Formulations, data formats and the model registry are on Formulations, Units and Registry. These names are defined in PowerfulCore.Foundation (or PowerfulCore itself) and exported by PowerfulCore.

PowerfulCore.Foundation.compute_observations — Function
compute_observations(sol::PowerFlowSolution, ::Type{ModelT}, var::Symbol) -> Vector{Float64}

Compute observation var for all instances of model type ModelT in the solution.

This is the primary API for models to provide derived outputs (power flows, generations, etc.) that are computed from the solved state rather than being direct state variables.

Arguments

  • sol::PowerFlowSolution: Complete power flow solution
    • sol.dae.y: State vector (voltages, angles)
    • sol.prob.sys: System model (parameters, topology)
    • sol.prob.address_manager: Variable address mapping
    • Residuals available via get_generator_residuals(sol) for power balance extraction
  • ::Type{ModelT}: Model type (e.g., Branch, PV, Slack, PQ)
  • var::Symbol: Observation variable name (defined in model's observations metadata)

Returns

  • Vector{Float64}: Values for all instances, length = number of model instances

Implementation Guidelines

  • Vectorized: Compute all instances at once for efficiency (use broadcasting, SIMD, etc.)
  • Complete access: Solution object provides everything needed (state, parameters, residuals)
  • Internal helpers allowed: Models can use scalar helpers internally if needed
  • Error handling: Throw descriptive error for unknown variable names

Example Implementations

# Simple case: direct computation from state and parameters
function compute_observations(sol::PowerFlowSolution, ::Type{Branch}, var::Symbol)
    branches = sol.prob.sys.models.Branch
    am = sol.prob.address_manager

    # Gather voltages for all branches (vectorized)
    theta_i = sol.dae.y[get_addresses(am, :Branch, :theta_i)]
    theta_j = sol.dae.y[get_addresses(am, :Branch, :theta_j)]
    v_i = sol.dae.y[get_addresses(am, :Branch, :v_i)]
    v_j = sol.dae.y[get_addresses(am, :Branch, :v_j)]

    # Compute power flows for all branches
    if var == :p_from
        return @. v_i^2 * branches.gi - v_i * v_j * (branches.gi * cos(theta_i - theta_j) + branches.bi * sin(theta_i - theta_j))
    # ... other variables
    end
end

# Complex case: extract from residuals
function compute_observations(sol::PowerFlowSolution, ::Type{Slack}, var::Symbol)
    slack = sol.prob.sys.models.Slack

    if var == :q_gen
        # Extract reactive power from bus power balance residuals
        g_gen = get_generator_residuals(sol)
        bus_indices = slack.i
        q_addrs = get_addresses(sol.prob.address_manager, :Bus, :q)
        return g_gen[q_addrs[bus_indices]]  # Vectorized gather
    end
end

Generic Fallback

This method provides a generic fallback that automatically handles:

  1. State variables: Extract from solution vector (e.g., :theta, :v for Bus)
  2. Parameters: Return from model struct (e.g., :pg for PV)

Models only need custom implementations for computed observations (e.g., power flows).

See Also

  • model_metadata: Defines observations available for each model
  • collect_model_table: Uses this API for report generation

PowerfulCore.Foundation.get_key_name — Method
get_key_name(::Type{M}) where M <: AbstractModel -> Symbol or Vector{Symbol}

Trait that specifies the field(s) that uniquely identify instances of a model type.

Key fields are used for:

  1. Indexing: Building external ID → internal index mappings
  2. Lookup: Finding specific instances by external identifier
  3. Group validation: Verifying model key fields match group interface

Returns

  • Symbol: Single key field (e.g., :i for Bus)
  • Vector{Symbol}: Composite key fields (e.g., [:i, :id] for PQ, [:i, :j, :ckt] for Branch)

Default Implementation

Throws ArgumentError - all models must implement this trait.

Examples

# Single key field (bus number)
get_key_name(::Type{Bus}) = :i

# Composite key (bus + load ID)
get_key_name(::Type{<:PQ}) = [:i, :id]

# Three-field composite key (from bus, to bus, circuit)
get_key_name(::Type{Branch}) = [:i, :j, :ckt]

See Also

  • model_metadata: Model structure metadata
  • validate_group_implementation: Uses key fields for group validation

PowerfulCore.Foundation.get_terminals — Method
get_terminals(::Type{ModelType}) -> Tuple{Terminal, ...}

Declare which vertices this model connects to in the network graph.

Terminal count determines behavior:

  • 0 terminals: Topological model (Area, Zone) - no spatial location
  • 1 terminal: Single-attachment device (PQ, PV) - island membership only
  • 2+ terminals: Multi-terminal device (Branch) - creates edges

Default returns empty tuple (no terminals).

Automata

The discrete behaviour of a model (modes, transitions, memory), declared in ModelMetadata.automata and ModelMetadata.memory. These names are public in PowerfulCore and not exported: import them by name (using PowerfulCore: Automaton, Mode, ...).

PowerfulCore.Foundation.NO_STATE_NAMES — Constant
check_automata(model::Symbol, automata, memory; states = Symbol[])

Throw an ArgumentError unless the automata and memory of model (collections of Automaton and MemoryQuantity, as ModelMetadata holds them) are well formed and realizable by Powerful's simulation, stating what is wrong and where:

  • what the semantic core requires: distinct modes that each hold the same discrete quantities; transitions between declared modes, returning to the mode they leave only where they set memory, with a condition or a crossing in a known direction; initial clauses naming declared modes, the last and only the last without a condition; held clauses naming declared modes; memory that starts at a value, and sets that set memory (memory no transition sets warns, being a parameter that stays what it starts at);
  • what Powerful needs: at least one initial clause (a start mode); names that are distinct across automata, discrete quantities and memory;
  • that the automata a value's continuity_writers name are automata of the model other than the transition's own, and that the value is one the transition holds (continuity or crossing_continuity);
  • that the values continuity holds at zero name what the automata compare: a transition's continuity and crossing_continuity surfaces are values it compares (an atom of its condition, or its guard), and the values held there and an automaton's at_rest are values the automata of the model compare;
  • and refuses what it does not realize: holds that are computed values rather than numbers (a discrete quantity changes only when a transition fires, and the core does not yet define a hold that reads the model), periodic crossings (Transition.period) and mode-dependent branch relations (Mode.relations);
  • that the states its modes govern (Mode.states) are differential states of the model (states: the names of its internal differential states), each governed once by a mode and by the modes of one automaton only, and that the right side of each is a finite number or a value (ValueRef). What the right side may read of the model is checked where the values are traced (PowerfulTDS check_governed).

PowerfulCore.Foundation.Automaton — Type
Automaton(name; modes, transitions, initial, held = [], at_rest = [])

Modes, the transitions between them, where the model starts (initial: the mode of the first InitialMode clause whose condition holds, the last clause having none) and the Held clauses. The discrete quantities of an automaton are those its modes hold.

at_rest names the values its conditions compare that a start from equilibrium holds at zero: the initialization makes them zero, whatever the data, flags and start modes (the rates of states it puts at rest; derived from the semantic core's continuity rules). A simulation decides the atoms over them at the start as the exact zero they are, not by the rounding of what is computed there.

Example: anti-windup lag

reach_upper = Atom(:y_minus_upper, :>=) & Atom(:rate, :>)
reach_lower = Atom(:y_minus_lower, :<=) & Atom(:rate, :<)
Automaton(:LAG;
    modes = [Mode(:free; holds = [:gate => 1]), Mode(:upper; holds = [:gate => 0]),
             Mode(:lower; holds = [:gate => 0])],
    transitions = [Transition(:free, :upper; when = reach_upper),
                   Transition(:free, :lower; when = reach_lower),
                   Transition(:upper, :free; when = Atom(:rate, :<)),
                   Transition(:lower, :free; when = Atom(:rate, :>))],
    initial = [InitialMode(:upper; when = reach_upper), InitialMode(:lower; when = reach_lower),
               InitialMode(:free)])

PowerfulCore.Foundation.Mode — Type
Mode(name; holds = [], relations = [], states = [])

One mode of an automaton and what each discrete quantity holds while the model is in it: holds maps each discrete quantity to a ValueRef. The simulation realizes numbers only and refuses a computed value (check_automata). relations (branch current => the residual that replaces its relation in this mode) mirrors the core's Mode.relations; Powerful has no multi-port branch contract, and its simulation refuses a mode that names any.

states (differential state => ValueRef) governs states: while the model is in the mode, each state it names is held on the right side, a number or a value the model computes in calc_automaton_values! (the core's Mode.relations of a state, solved for the state: in the semantic core's bounded, the bound). The transition that enters the mode writes the right side to the state at that instant (a projection along the governed state alone, project_states!), and the model's rate for the state, in the mode, is the rate of the right side (the model's, gated by what the mode holds). The right side must be affine in differential states with constant coefficients and read nothing else of the model's evolving quantities (check_governed of PowerfulTDS refuses the others, naming the mode and the state).

Example

Mode(:upper; holds = [:gate => 0], states = [:y => :upper_bound])   # y = upper_bound while here

PowerfulCore.Foundation.Transition — Type
Transition(from, to; when = nothing, guard = nothing, direction = nothing,
           period = nothing, sets = [], continuity = [], crossing_continuity = [],
           continuity_writers = [])

from to to either where the condition when holds (a condition transition: it fires at the first instant when holds while the model is in from, at the start, right after another transition or where it becomes true), or where the value guard crosses zero in direction (:rising from below, :falling from above; a crossing transition). period (a periodic crossing) mirrors the core's Transition.period; the simulation refuses it.

sets maps memory to the ValueRef it takes when the transition fires. Every right side reads the quantities as they were before the transition (the assignments are simultaneous) and the time of the transition. A transition may return to the mode it leaves only where it sets memory.

continuity (surface => values) names, for a value surface the transition compares (an atom of its condition, or its guard), the values continuity holds at zero where the transition fires on the zero of surface: each vanishes wherever the model, in from, is on that surface, and the transition leaves the algebraic state where it is, so each is zero after it too (derived from the semantic core's continuity rules: REGCA1's dq on entering its clamp at v = Volim). A simulation decides the atoms over them at that instant by their rate in the discrete state the transition enters, not by their value, which is zero there to the rounding of the reinitialization.

crossing_continuity has the form of continuity and the same meaning, for facts that hold only where the transition fires at a crossing located while the simulation was integrating its source mode from (the first round of an instant): the source mode was settled before the instant, so none of its other exits held. REGCA1's high-voltage clamp, released where dq reaches zero, holds Vt - Volim at zero only from a settled clamp: its exit to floor not holding there is what makes the clamp's reactive power and the clear mode's agree. A clamp entered earlier in the same instant has no such guarantee. The values are decided by their rate at that crossing, as with continuity, and never when the transition fires in a later round of the instant, at a start, at an event's reinitialization or at any other instant. continuity holds however the source mode was entered (derived the same way).

continuity_writers (value => automata) names, for a value held by continuity or crossing_continuity on this transition, the automata of the same instance whose firing voids that value's hold: the value reads a quantity one of them writes (REECA1's PI clip holds values that read the limit Iqmax, which two other automata can write), so that the fact derived without their firing no longer holds where one fires. A simulation holds the value only where none of the listed automata fires in the round of the transition (the algebraic point is solved again between rounds, so an earlier round's writer is in the point the round reads), and decides it by its own value otherwise, as it does a value no marker names. A value not listed has no writers.

A marker of any kind for a value that reads a quantity the network solves (a variable without mass) is not applied in a round in which another transition, of any instance, changes a quantity delivered to the network: the derivation reads the inputs of the model as unchanged across the transition, and what other devices do reaches them through the network. Each listed value is one the transition holds, each automaton is one of the model, and the transition's own automaton is not listed (it fires at most once per round, so it is never a value's writer).

PowerfulCore.Foundation.DynamicModel — Constant
DynamicModel <: PowerSystemComponent

Interface for models with differential equations. Includes synchronous machines, controllers, dynamic loads.

Inherits all requirements from PowerSystemComponent.

Required Methods

In addition to PowerSystemComponent requirements, models implementing this interface must define:

  • calc_residuals!(ws::ResidualBuffers, model::StructArray, external::NamedTuple, formulation::FormulationTrait)

    Calculate DAE residuals (differential + algebraic).

    Computes:

    • State derivatives: f(x, y) for dx/dt = f(x, y)
    • Algebraic equations: g(x, y) = 0

    Note: Uses same 4-parameter signature as PowerFlowModel for consistency. TDS currently uses PowerInjection formulation, but signature is standardized.

  • initialize_dynamic_states(model::StructArray{<:AbstractModel}, links::ModelLinks, source_model::Symbol, sys::SystemModel, pf_sol::PowerFlowSolution) -> NamedTuple

    Initialize state variables from power flow solution (batch/vectorized).

    Takes power flow solution and model links, computes initial conditions for differential states (e.g., rotor angle, speed, flux linkages) for all instances at once using vectorized data gathering.

    Returns NamedTuple with initial values for all state variables.

Optional Trait Methods

  • requires_initialization(::Type{T}) -> Bool where T <: AbstractModel

    Trait, declared by every model (no default): true if initialize_dynamic_states should be called. Models without states of their own (e.g., Slack) declare false.

  • get_dyr_model_name(::Type{T}) -> Union{String, Nothing} where T <: AbstractModel

    Return DYR model name string for PSS/E DYR file parsing. Examples: "GENCLS", "GENROU", "EXST1" Returns nothing if model is not parseable from DYR files. Used by DYR parser to auto-discover available models.

  • get_replacement_map(::Type{T}) -> Dict{Symbol, NamedTuple} where T <: AbstractModel

    Declare which static models this replaces in TDS.

    Returns Dict{Symbol, NamedTuple} mapping:

    • Keys: static model types (:PV, :Slack)
    • Values: (source_fields=(...), target_fields=(...))

    Example: Dict(:PV => (source_fields=(:BUS, :ID), target_fields=(:i, :id))) Used for linking DYR models to power flow generators.

  • get_data_inheritance(::Type{T}) -> Dict{Symbol, Dict{Symbol, Symbol}} where T <: AbstractModel

    Declare data to inherit from linked power flow models.

    Returns Dict{Symbol, Dict{Symbol, Symbol}}:

    • Outer keys: source model types (:PV, :Slack)
    • Inner dicts: destinationfield => sourcefield mappings

    Example: Dict(:PV => Dict(:xd_p => :zx)) # Inherit PV.zx → GENCLS.xd_p

  • parse_dynamic_model(::Type{T}, dyr_data, sys_pf::SystemModel, links::Union{ModelLinks, Nothing}) -> StructArray{T} where T <: AbstractModel

    Parse dynamic model from DYR data.

    For replacement models (GENCLS, GENROU): Pass ModelLinks to inherit data from PV/Slack. For controller models (TGOV1, EXST1): Pass nothing - linking deferred to TDS setup via group reference terminals.

    Returns StructArray{T} with all model instances.

Implementation Requirements

Models implementing DynamicModel should have:

  • At least one state variable in their metadata
  • Implementation of both calc_residuals! and initialize_dynamic_states
  • Appropriate trait methods (e.g., requires_initialization returning true)

See Also

  • GeneratorModel: Semantic marker for generator models

PowerfulCore.Foundation.PowerFlowModel — Constant
PowerFlowModel <: PowerSystemComponent

Interface for models participating in power flow analysis. Includes static loads, generators, network elements.

Inherits all requirements from PowerSystemComponent.

Required Methods

In addition to PowerSystemComponent requirements, models implementing this interface must define:

  • calc_residuals!(ws::ResidualBuffers, model::StructArray, external::NamedTuple, formulation::FormulationTrait)

    Calculate residual contributions for power flow equations.

    Models implement this for each formulation they support. Julia's multiple dispatch selects the right method based on formulation type.

    Common formulations:

    • PowerInjection: P-θ, Q-V (polar coordinates)
    • CurrentInjection: Ir-Vr, Ii-Vi (rectangular)
    • DCPowerFlow: P-θ only (DC approximation)

Optional Methods

  • supports_formulation(::Type{T}, ::Type{F}) -> Bool where {T <: AbstractModel, F <: FormulationTrait}

    Query if model supports a specific formulation. Optional trait for capability introspection. If not implemented, caller must rely on Julia's method dispatch.

  • compute_observations(sol::PowerFlowSolution, ::Type{T}, var::Symbol) -> Vector{Float64} where T <: AbstractModel

    Compute derived outputs from solution (vectorized).

    Required only if model declares observations in metadata. Examples: power flows in branches, reactive power from PV generators.

    Returns Vector{Float64} with values for all model instances.

  • get_terminals(::Type{T}) -> Tuple where T <: AbstractModel

    Declare terminal connections to network vertices (buses/nodes).

    Returns tuple of Terminal objects specifying connectivity. Used for topology analysis and external parameter retrieval.

    Examples:

    • Load: (Terminal(:Bus, :i),) - single attachment
    • Branch: (Terminal(:Bus, :i), Terminal(:Bus, :j)) - two terminals

Implementation Requirements

Models implementing PowerFlowModel should have:

  • Non-empty residuals in their metadata (at least one algebraic equation)
  • Implementation of calc_residuals! for at least one formulation

See Also

  • LoadModel: Semantic marker for load models
  • NetworkElement: Semantic marker for network topology elements

PowerfulCore.Foundation.PowerSystemComponent — Constant
PowerSystemComponent

Base interface for all power system models. Covers fundamental model identification and metadata.

Required Methods

Models implementing this interface must define:

  • model_metadata(::Type{T}) -> ModelMetadata where T <: AbstractModel

    Return ModelMetadata describing model structure. Every model MUST implement this. It declares:

    • Variables (state and algebraic)
    • Residuals (equations)
    • Parameters (for per-unit conversion)
    • Observations (computed outputs)
    • External parameters (data from other models)

  • get_key_name(::Type{T}) -> Vector{Symbol} where T <: AbstractModel

    Return composite key field names for model instances.

    Examples:

    • Bus: [:i] (bus number only)
    • PQ: [:i, :id] (bus number + load id)
    • Branch: [:i, :j, :ckt] (from bus, to bus, circuit id)

Optional Methods

  • supports_format(::Type{T}, ::Type{F}) -> Union{FormatSupport{F}, NoFormatSupport} where {T <: AbstractModel, F <: DataFormat}

    Check if model can be parsed from a data format (PSSE, PSSEDYR, etc.). Returns FormatSupport{F}() if supported, NoFormatSupport() otherwise. Used by parser to discover which models to parse from each file type.

  • get_status_field(::Type{T}) -> Union{Symbol, Nothing} where T <: AbstractModel

    Return status field name if model has device status tracking. Returns :status or nothing. Status fields indicate if device is in-service (true/1) or out-of-service (false/0).

PowerfulCore.Foundation.check_parameter_domains — Function
check_parameter_domains(x::M, from::AbstractString) where M <: AbstractModel -> M

Check that every parameter of the instance x lies in its valid domain (ranges, ordering between limits, divisors that must not be zero), throwing ArgumentError naming from (where the values came from, e.g. "keyword construction" or a FieldModification's description) if not. Every model declares it: there is no default, since a model without a declaration would let an event set a parameter to an invalid value with no check. A model with no domain constraints of its own declares check_parameter_domains(x::M, ::AbstractString) = x and says so in a comment; one with constraints (typically generated with the model from its DSL source) checks them.

PowerfulCore.Foundation.requires_initialization — Function
requires_initialization(::Type{<:AbstractModel}) -> Bool

Whether the time-domain initialization calls the model's initialize_dynamic_states, which gives its states and setpoints: true for the machines, controls and converters; false for a model with no state of its own (the power flow models, whose variables are the bus voltages of the power flow) or whose states another initializer owns entirely. Every model declares it: there is no default, since a model with states that is not initialized would start them at zero. The initialization refuses a system holding a model without a declaration, naming it, before it initializes any model.

Model Groups

PowerfulCore.Foundation.GroupInterface — Type
GroupInterface

Defines the contract that all models in a group must satisfy.

Acts as a "trait bundle" for a category of models. Models declare they implement a group interface, and the system validates they provide the required variables and residuals. A model initialized from a member of the group (InitInput of kind :from_group_init) reads the initial value of one of its required variables, through the member's group_var_mapping.

Fields

  • name::Symbol: Group name (e.g., :generators, :governors, :exciters)
  • required_vars::Vector{GroupVar}: Variables all members must expose
  • required_residuals::Vector{GroupRes}: Residuals all members must expose
  • optional_residuals::Vector{GroupRes}: Residuals a member may expose; a model that delivers through one is routed to a member that has it (InjectionForms)
  • key_fields::Vector{Symbol}: Composite key for matching (e.g., [:BUS, :ID])

Example

GroupInterface(
    name = :generators,
    required_vars = [
        GroupVar(:omega, :state; description="Rotor speed"),
        GroupVar(:delta, :state; description="Rotor angle"),
        GroupVar(:P_m, :algebraic; description="Mechanical power input"),
    ],
    required_residuals = [
        GroupRes(:g_P_m, :algebraic, :shared; description="Mechanical power residual"),
    ],
    key_fields = [:BUS, :ID]
)

get_base_quantity_vector(sys::SystemModel, model_name::Symbol,

Get per-instance base quantity values for a model using the trait system.

Arguments

  • sys: SystemModel with solved power flow
  • model_name: Name of the model (e.g., :Bus, :PQ)
  • base_type: Type of base quantity (e.g., BaseVoltage, BasePower)
