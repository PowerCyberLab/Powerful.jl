Implementing Models

A practical guide to adding new device models. Following these patterns gives a model power flow, time-domain simulation, automatic differentiation and reporting support, and a dispatch point for every array type a workspace is specialized for.

The reference implementations are the hand-written static models in PowerfulPF/src/models/, in particular pq.jl, pv.jl and branch.jl. The code excerpts below are taken from pq.jl.

Generated dynamic model files

The files genrou.jl (in PowerfulTDS/src/models/generators/), sexs.jl (exciters/) and tgov1.jl (governors/) are generated by a model compiler that is not part of this repository; their headers say "DO NOT EDIT". gencls.jl, gensal.jl and gentpj1.jl started as its output and are hand-maintained now, as their headers say. All follow the same metadata and kernel pattern as hand-written models. New models are written by hand following this guide.

The Model Interface

Part 1: Struct Definition

Pattern (abridged from PQ):

@kwdef mutable struct PQ{Tv} <: AbstractModel
    # Structural fields (concrete types)
    i::Int32           # Bus number (external ID)
    id::String3        # Load identifier
    status::Bool       # In-service flag

    # Numerical fields (type parameter)
    pl::Tv             # Constant power P
    ql::Tv             # Constant power Q
    ip::Tv             # Constant current P
    iq::Tv             # Constant current Q
    yp::Tv             # Constant admittance P
    yq::Tv             # Constant admittance Q
    # ... area, zone, owner, scale, intrpt
end

Rules:

  • Subtype AbstractModel
  • Use @kwdef mutable struct (keyword constructors, modifiable)
  • Type parameter Tv for numerical fields
  • Concrete types for structural fields (Int32, String3, Bool)
  • Store external IDs, not internal indices
  • Include a status field

Why a type parameter: The same struct works with Float64 and with other number types (e.g. Float32, ForwardDiff.Dual when differentiating with respect to parameters).

Part 2: Model Registration

@register_model PQ

Makes the model available to all_models() for system discovery.

Inside a package, @register_model collects the types at precompile time; the package calls @init_model_registry before including its model files and register_pending_models!(_PENDING_MODELS) in its __init__() (see PowerfulPF/src/PowerfulPF.jl).

Part 3: Keys and Connectivity

# Composite key identifying an instance (used by events, lookups, linking)
get_key_name(::Type{T}) where T<:PQ = [:i, :id]

# Single-attachment device
const PQ_TERMINALS = (Terminal(:Bus, :i),)

get_terminals(::Type{<:PQ}) = PQ_TERMINALS

Traits such as get_terminals, get_key_name, model_metadata and calc_residuals! are defined in PowerfulCore; a package extends them with import PowerfulCore: model_metadata, calc_residuals!, get_terminals, get_key_name.

For multi-terminal devices:

# Branch: two-terminal device
const BRANCH_TERMINALS = (
    Terminal(:Bus, :i),  # From-bus
    Terminal(:Bus, :j)   # To-bus
)

For group references and composite keys:

# Dynamic models attach to whatever implements the bus group (Bus, or another model
# that provides the same interface)
Terminal(:bus_group, :BUS)

# Controllers match their generator by bus number + machine ID
Terminal(:generators, [:BUS, :ID])

Injection ports. A model delivers its injection to :bus_group through residuals of the group: p, q (power, required of every bus model), ip, iq (current, optional: in phase with and in quadrature to the bus voltage, positive into the bus, p = v ip, q = v iq), or jr, ji (voltage, optional: a model that is an EMF E behind an impedance Z declares its short-circuit current J = E/Z, network frame). The model declares one form, its natural one (InjectionForms in its metadata; a model of power form needs none: every bus takes it), and computes the others from it. REGCA1 declares the current form, with power as a fallback (InjectionForms(:current, power = [:p_inj, :q_inj], current = [:ip_inj, :iq_inj])). The machines (GENROU, GENSAL, GENTPJ1, GENCLS) declare the voltage form, with power and current as fallbacks (InjectionForms(:voltage, power = [:p_inj, :q_inj], current = [:ip_inj, :iq_inj], voltage = [:jr_inj, :ji_inj])): a model of the voltage form reads its port voltage (v_port, theta_port), and a bus maps it to its own voltage, so the model's current (E − V)/Z realizes the form algebraically.

Each connection is delivered through exactly one port, chosen when the addresses are retrieved (injection_routes): the bus's port in the model's natural form if it implements it, otherwise (voltage) the current port and then the power port, or (power, current) the other one, and a bus implementing none is an error. The residuals of the forms not delivered have the address UNROUTED for that instance and are not scattered. REGFM_A1 declares the same two ports as REGCA1 (current, with power as a fallback): at a bus that implements only the power port, its injection still routes through it.

Composite keys are used when a controller (TGOV1) needs to find its target (GENCLS/GENROU/...) across heterogeneous model types in a group.

Terminals are the single source of truth for topology analysis, index linking and external parameter retrieval.

Group key names: Group interfaces define key_fields (e.g. [:BUS, :ID] for :generators). A model that implements the group with different key field names is accepted with a warning and matched by position. For new models, prefer the group's key names.

Controller links: Controllers expose their links through terminals on the controlled group. All links go through the same foreign_refs/GroupLinkRef path (see Three-Layer Indexing).

Part 4: Metadata Declaration

function model_metadata(::Type{PQ})
    metadata = ModelMetadata(
        name = :PQ,
        vars = PQ_VARS,
        observable_vars = PQ_observable_vars,
        residuals = PQ_RESIDUALS,
        params = PQ_PARAMS,
        observations = PQ_OBSERVATIONS,
        ratings = PQ_RATINGS,
        ext_params = PQ_EXT_PARAMS,
        status_field = :status,
    )

    # Formulation overrides
    metadata.vars_by_formulation[CurrentInjection] = PQ_VARS_CURRENT
    metadata.residuals_by_formulation[CurrentInjection] = PQ_RESIDUALS_CURRENT
    metadata.vars_by_formulation[DCPowerFlow] = PQ_VARS_DC
    metadata.residuals_by_formulation[DCPowerFlow] = PQ_RESIDUALS_DC

    return metadata
end

Fields of ModelMetadata (PowerfulCore/src/foundation/core_types.jl):

  • vars - Variables to allocate in (or reference from) the DAE vectors
  • observable_vars - Computed outputs stored in the workspace without DAE addresses
  • residuals - Equations this model contributes to
  • params - Fields that need per-unit conversion
  • observations - Report outputs computed by compute_observations
  • ratings - Device ratings used as conversion bases (e.g. MVA base)
  • ext_params - Values retrieved from other models
  • initialized_params, init_inputs - Setpoints and power flow inputs for dynamic model initialization
  • variable_limits - Bounds of limited variables (VariableLimit), checked at initialization
  • automata, memory - Discrete behaviour: modes, transitions, and values kept between them
  • status_field - The Bool field that indicates in-service
  • evaluation_pass - Evaluation order (default 0; later passes run after earlier ones)

Variables and Residuals

Variable Declarations

Foreign variables (owned by another model):

const PQ_VARS = [
    ModelVar(
        :theta,                # Local name in workspace
        AlgebVar(),            # Address type
        :Bus,                  # Source model that owns it
        :theta,                # Variable name in source model
        :i;                    # Field holding the foreign key
        description="Bus voltage phase angle",
        units="rad",
    ),
    ModelVar(
        :v,
        AlgebVar(),
        :Bus,
        :v,
        :i;
        description="Voltage magnitude",
        units="pu",
    ),
]

Owned variables (typical for dynamic models):

ModelVar(:delta, StateVar(); description="Rotor angle", units="rad")

# A differential state with a mass coefficient (M dx/dt = f), from GENCLS
ModelVar(:omega, StateVar(); description="Rotor speed (pu)",
         mass_coefficient=MassCoefficient(m -> 2.0 .* m.H))

Address types:

  • AlgebVar() - Algebraic variable (in y)
  • StateVar() - Differential state (in x)

Residual Declarations

Accumulation mode (SharedRes):

const PQ_RESIDUALS = [
    ModelResidual(
        :p,                    # Local residual name
        AlgebRes(),            # Address type
        SharedRes(),           # Accumulation mode (default :add)
        :Bus,                  # Target model
        :p,                    # Residual name in target
        :i,                    # Foreign key to target
        description="Active power injection from load",
    ),
    ModelResidual(
        :q,
        AlgebRes(),
        SharedRes(),           # g[addr] += residual
        :Bus,
        :q,
        :i,
        description="Reactive power injection from load",
    )
]

Setter mode (control equations), from PV:

ModelResidual(
    :v_ctrl,
    AlgebRes(),
    SharedRes(:set),           # g[addr] = residual (overwrites)
    :Bus,
    :q,                        # Replaces the Q balance at PV buses
    :i,
    description="Voltage magnitude control equation (replaces Q balance)",
)

Private residuals (equations of the model's own variables):

ModelResidual(:ddelta, StateRes(), PrivateRes(); description="Rotor angle")

Access modes:

  • SharedRes() or SharedRes(:add) - Accumulate (multiple devices contribute)
  • SharedRes(:set) - Overwrite (control equations), applied after the :add contributions
  • PrivateRes() - The model's own equation
Explicit Algebraic Equation Form (Required for Y-bus Solver)

Controller algebraic equations must use the explicit form g = f - y:

# CORRECT: g_P_m = P_m0 - P_m (explicit form)
outputs.g_P_m[i] = mask * (params.P_m0[i] - vars.P_m[i])

# WRONG: g_P_m = P_m - P_m0 (inverted sign)
outputs.g_P_m[i] = mask * (vars.P_m[i] - params.P_m0[i])

Why: The Y-bus solvers (PowerfulYbus) move these algebraic variables by a Newton iteration on all the algebraic rows and the network equations together (y -= J⁻¹ g, with J = ∂g/∂y the sparse Jacobian taken by ForwardDiff). For a residual of the form g = (target) - (variable), the entry of its own variable is -1 and the step is y + g = target where nothing else moves; a row that does not read its own variable is solved too, as long as the Jacobian of the whole system is nonsingular (the coupling through the network is in it).

Naming convention: Residual :g_foo pairs with variable :foo. The Y-bus solver discovers these pairs from metadata (_algebraic_pairs in PowerfulYbus/src/integration/ybus_tds_problem.jl, AlgebraicNewton).

Applies to: Generator control inputs (P_m, E_q), governor outputs (pref, pout) and any controller algebraic variable that follows the "hold at setpoint" pattern.

Parameter Specifications

For per-unit conversion:

const PQ_PARAMS = [
    ModelParam(:pl, PowerNominal, description="Constant power P", units="MW"),
    ModelParam(:ql, PowerNominal, description="Constant power Q", units="MVAR"),
    ModelParam(:ip, PowerNominal, description="Constant current P", units="MW"),

During SystemModel construction:

  • Fields are converted from physical units (MW, kV) to per-unit
  • The conversion coefficients are stored in sys.pu_coeffs
  • The original values are kept in sys.parsed_data

External Parameter Declarations

Retrieve values from other models:

const PQ_EXT_PARAMS = [
    ExtParam(:basekv, PQ_TERMINALS[1], :basekv, BaseVoltage(), PrePerUnit(),
             required=true, description="Connected bus base voltage"),
    ExtParam(:ide, PQ_TERMINALS[1], :ide, Dimensionless(), PrePerUnit(),

Retrieval phases:

  • PrePerUnit() - Before per-unit conversion (dimensionless values, bases)
  • PostPerUnit() - After conversion (quantities that must already be in per-unit)

Access in residual calculations through the external argument of calc_residuals!:

external.vm[i]  # Case voltage of the bus of the i-th load (used by the DC kernel)

The Residual Kernel Pattern (Required)

Three parts for every model:

Part 1: Pure Computational Kernel (CPU)

@inline function pq_residual_kernel!(
    outputs::NamedTuple{(:p, :q)},
    params::NamedTuple{(:pl, :ql, :ip, :iq, :yp, :yq, :vmin)},
    vars::NamedTuple{(:v,)},
    active::AbstractVector{Bool},
    ::Type{<:Vector}  # CPU dispatch
)
    @inbounds @simd for i in eachindex(outputs.p)
        mask = active[i]  # Branchless masking

        # ZIP load: P = pl·f(v) + ip·v + yp·v², f = constant-power factor below vmin
        power = calc_zip_load(vars.v[i], params.pl[i], params.ql[i],
                              params.ip[i], params.iq[i], params.yp[i], params.yq[i], params.vmin)

        # Sign convention: load consumption = negative injection into bus
        outputs.p[i] = mask * (-power.p)
        outputs.q[i] = mask * (-power.q)
    end

    nothing
end

Key points:

  • Pure function of NamedTuples of arrays (and scalars such as vmin)
  • Branchless masking: mask * value (not if active[i])
  • @inbounds @simd for vectorization
  • ::Type{<:Vector} selects the CPU method
  • Physics in a separate function (calc_zip_load) shared by the CPU kernel, the GPU kernel and reporting
  • Injection sign convention: positive = into the bus

Part 2: GPU Kernel

A GPU extension adds a method of the same kernel function, dispatched on the GPU array type, plus the CUDA device function it launches:

import PowerfulPF: pq_residual_kernel!, calc_zip_load

# Device kernel
function pq_residual_cuda_kernel!(
    outputs_p, outputs_q,
    params_pl, params_ql, params_ip, params_iq, params_yp, params_yq, vmin,
    vars_v, active, n
)
    i = threadIdx().x + (blockIdx().x - 1) * blockDim().x
    if i <= n
        mask = active[i] ? one(eltype(outputs_p)) : zero(eltype(outputs_p))
        power = calc_zip_load(vars_v[i], params_pl[i], params_ql[i],
                              params_ip[i], params_iq[i], params_yp[i], params_yq[i], vmin)
        @inbounds outputs_p[i] = mask * (-power.p)
        @inbounds outputs_q[i] = mask * (-power.q)
    end
    return nothing
end

# Launcher
@inline function pq_residual_kernel!(
    outputs::NamedTuple{(:p, :q)},
    params::NamedTuple{(:pl, :ql, :ip, :iq, :yp, :yq, :vmin)},
    vars::NamedTuple{(:v,)},
    active::AbstractVector{Bool},
    ::Type{<:CUDA.CuArray}  # GPU dispatch
)
    n = length(outputs.p)
    (; threads, blocks) = cuda_kernel_config(n)
    CUDA.@cuda threads=threads blocks=blocks pq_residual_cuda_kernel!(
        outputs.p, outputs.q,
        params.pl, params.ql, params.ip, params.iq, params.yp, params.yq, params.vmin,
        vars.v, active, n
    )
    nothing  # kernels run in order on the default stream
end

Key points:

  • Same physics as the CPU version (same physics function)
  • Thread indexing instead of loops
  • ::Type{<:CuArray} selects the GPU method

Part 3: Data Adapter (calc_residuals!)

@inline function calc_residuals!(
    ws::ResidualBuffers{T, AT},
    pq::StructArray{<:PQ},
    _external::NamedTuple,
    ::PowerInjection,             # Formulation dispatch
    t = zero(T);                  # Simulation time
    active_mask::AbstractVector{Bool}
) where {T, AT}
    pq_residual_kernel!(
        (p = ws.res_vals.p, q = ws.res_vals.q),              # Outputs from workspace
        (pl = pq.pl, ql = pq.ql, ip = pq.ip, iq = pq.iq, yp = pq.yp, yq = pq.yq,
         vmin = ws.system.constant_power_vmin),              # Params from model and system
        (v = ws.var_vals.v,),                                # Variables from workspace
        active_mask,                                         # In-service mask (passed in)
        AT                                                   # Dispatch type parameter
    )
end

Key points:

  • Extracts arrays from the workspace, the model and the system settings (ws.system)
  • Calls the kernel with NamedTuples
  • active_mask is a keyword argument supplied by the system workspace; it is not stored in ResidualBuffers
  • Dynamic models read initialization setpoints from ws.setpoints
  • AT enables automatic CPU/GPU dispatch
  • No computation in this layer

For multiple formulations, add one adapter per formulation:

# CurrentInjection
@inline function calc_residuals!(
    ws::ResidualBuffers{T, AT},
    pq::StructArray{<:PQ},
    _external::NamedTuple,
    ::CurrentInjection,
    t = zero(T);
    active_mask::AbstractVector{Bool}
) where {T, AT}
    pq_current_kernel!(  # Different kernel, different physics
        (i_r = ws.res_vals.i_r, i_i = ws.res_vals.i_i),
        (pl = pq.pl, ql = pq.ql, ip = pq.ip, iq = pq.iq, yp = pq.yp, yq = pq.yq,
         vmin = ws.system.constant_power_vmin),
        (v_r = ws.var_vals.v_r, v_i = ws.var_vals.v_i),
        active_mask,
        AT
    )
end

Observations and Reporting

Computed outputs (not in the DAE vector):

const PQ_OBSERVATIONS = [
    ModelObservable(:p_consumed, ActivePower, units="pu",
                    description="Active power consumed", default_output=true),
    ModelObservable(:q_consumed, ReactivePower, units="pu",
                    description="Reactive power consumed", default_output=true),
]

Implement the computation:

function compute_observations(sol::PowerFlowSolution, ::Type{<:PQ}, var::Symbol)
    pq = sol.prob.sys.models.PQ
    vmin = sol.prob.sys.settings.constant_power_vmin

    # Voltage magnitudes for all loads, extracted once
    v_addrs = get_addresses(sol.prob.address_manager, :PQ, :v)
    v_vals = sol.dae.y[v_addrs]

    n = length(pq)
    result = Vector{Float64}(undef, n)

    @inbounds for i in 1:n
        # Same physics function as the residual kernel
        power = calc_zip_load(v_vals[i], pq.pl[i], pq.ql[i],
                              pq.ip[i], pq.iq[i], pq.yp[i], pq.yq[i], vmin)
        if var == :p_consumed
            result[i] = power.p
        elseif var == :q_consumed
            result[i] = power.q
        else
            error("Unknown PQ output variable: $var")
        end
    end

    return result
end

Key points:

  • Compute all instances at once
  • Extract addresses once, not per instance
  • Reuse the physics function from the residual kernel

Common Patterns

Simple Algebraic Model (PQ Load)

  • Foreign variables only (theta, v from Bus)
  • SharedRes() for power balance
  • Multi-formulation support
  • ZIP load physics

Reference: PowerfulPF/src/models/pq.jl

Control Model (PV Generator)

  • Foreign variables from Bus
  • SharedRes() for the power injection
  • SharedRes(:set) for voltage control (replaces the Q balance)
  • evaluation_pass = 1, so in CurrentInjection it reads the currents accumulated by pass-0 models

Reference: PowerfulPF/src/models/pv.jl

Network Element (Branch)

  • Foreign variables from both ends (i and j buses)
  • SharedRes() contributions to both buses
  • Different formulations change the expressions

Reference: PowerfulPF/src/models/branch.jl

Dynamic Model (GENCLS)

  • Owned StateVar variables (rotor angle, speed) with private residuals
  • Foreign algebraic variables (terminal voltage) through :bus_group
  • Replaces a static PV/Slack generator (get_replacement_map, get_data_inheritance)
  • Initialization from the power flow (init_inputs, initialized_params)

Reference: PowerfulTDS/src/models/generators/gencls.jl

Controller Model (TGOV1)

  • Controls generators via the get_controlled_group() trait
  • Linked through a terminal on the controlled group in get_terminals()
  • Reads initialization data from the target's initialization (InitInput of kind :from_group_init)

Required traits for controllers:

# Which group this controller targets
get_controlled_group(::Type{<:TGOV1}) = :generators

# Composite key for matching (must be defined explicitly)
get_terminals(::Type{<:TGOV1}) = (Terminal(:generators, [:BUS, :ID]),)

Reference: PowerfulTDS/src/models/governors/tgov1.jl

Implementing Anti-Windup Limits

Dynamic models often have state variables that must stay within bounds (e.g. the REECA1 power order PMIN ≤ s5_y ≤ PMAX). A limited state is an automaton (see Implementing Automata): the generated models (SEXS, TGOV1, REECA1, REGCA1) state their anti-windup that way. It has three parts: the automaton, the kernel that reads its gate, and the declaration of the bounds.

1. The Automaton

Three modes hold a gate that multiplies the rate of the state: free (gate 1), and upper and lower (gate 0). A free state reaching a limit with its unlimited rate pointing beyond it is held there, and a held state is released where its unlimited rate turns inward:

reach_upper = Atom(:y_upper, :>=) & Atom(:rate, :>)   # y ≥ upper and rate > 0
reach_lower = Atom(:y_lower, :<=) & Atom(:rate, :<)
automata = [Automaton(:LAG;
    modes = [Mode(:free; holds = [:gate => 1]), Mode(:upper; holds = [:gate => 0]), Mode(:lower; holds = [:gate => 0])],
    transitions = [Transition(:free, :upper; when = reach_upper), Transition(:free, :lower; when = reach_lower),
                   Transition(:upper, :free; when = Atom(:rate, :<)), Transition(:lower, :free; when = Atom(:rate, :>))],
    initial = [InitialMode(:upper; when = reach_upper), InitialMode(:lower; when = reach_lower), InitialMode(:free)])]

The transitions are located: the simulation finds where y - upper or lower - y crosses zero, and where the unlimited rate turns inward, and restarts the integrator there. At the start and after every event the transitions apply at once, so a condition that starts on its other side is no crossing. A held state has a zero rate wherever its unlimited rate points outward, so the release must be located, or a step whose ends both do would pass over the interval where the state should move inward.

2. The Kernels

calc_residuals! multiplies the rate by the gate (ws.automata.discrete.gate), and calc_automaton_values! computes the atoms into ws.automata.values: the unlimited rate and the distances y - upper and y - lower of the state from its limits. Keep the expressions branch-free and AD-compatible: within an integration step the equations do not switch, and the Jacobian is that of the mode.

out.dy[i] = active[i] * p.gate[i] * (u - v.y[i]) / p.T[i]        # residual kernel
vals.rate[i] = (u - v.y[i]) / p.T[i]                              # values kernel
vals.y_upper[i] = v.y[i] - p.upper[i]
vals.y_lower[i] = v.y[i] - p.lower[i]

3. The Bounds

The limited state is declared with its bounds as a VariableLimit (variable_limits = [VariableLimit(:LAG_y, :Vmin, :Vmax)]). The initialization checks the initial value of the variable against them (enforce_initial_limits!): a violated bound that names a model field is moved to the value with TDSConfig(adjust_limits = true), and the start is computed again; otherwise the violation is an error. A bound may also be computed from the parameters (m -> 2 .* m.Vmax), and then cannot be moved to a violating initial value.

Testing Limits

Verify a limit by:

  1. Creating a scenario that pushes the state to its limit
  2. Confirming the state stays at the limit (within tolerance)
  3. Creating a scenario that reduces demand
  4. Confirming the state comes back off the limit

For a lag with a known input the trajectory has a closed form, against which the switching times and the trajectory are checked (Powerful/test/tds/test_automata.jl).

Implementing Automata

A model with discrete behaviour (relays, timers, protection, anti-windup) declares automata and memory in its metadata (ModelMetadata(; automata, memory), see PowerfulCore/src/foundation/automata.jl): modes that hold values of its discrete quantities, transitions between them on conditions of atoms (a value compared with zero) or crossings of guards, and memory that transitions set. Two kernels in the pattern above read the discrete state from the workspace's AutomatonState (ws.automata):

  • calc_residuals! reads the discrete quantities (ws.automata.discrete) and memory (ws.automata.memory) of each instance where its equations depend on them;
  • calc_automaton_values! computes every value the automata name (the atoms a - b, crossing guards, and the sets and memory starts that are not numbers) into ws.automata.values, from the same inputs.
# A relay on x: on above hi, off below lo; z integrates the time on (r = 1 while on)
automata = [Automaton(:relay; modes = [Mode(:off; holds = [:r => 0]), Mode(:on; holds = [:r => 1])],
    transitions = [Transition(:off, :on; when = Atom(:x_hi, :>)), Transition(:on, :off; when = Atom(:x_lo, :<))],
    initial = [InitialMode(:off)])]
# calc_residuals!:        ws.res_vals.dz .= active_mask .* ws.automata.discrete.r
# calc_automaton_values!: ws.automata.values.x_hi .= ws.var_vals.x .- m.hi
#                         ws.automata.values.x_lo .= ws.var_vals.x .- m.lo

The contract of the kernels. Both kernels compute what belongs to instance i from the variables, parameters, setpoints, external parameters and instance i's own discrete quantities and memory only, never from another instance's (a rate r[1] * r[2] breaks it). Then, with the state fixed, a switch of one instance changes that instance's rates alone, and switches of several instances at one instant (identical devices tripping together) combine without interacting: evaluating the automaton with dual numbers at the instant differentiates through them with one switching time per instance, and a settle after a located event considers only the instances that switched. Every simulation checks the contract for the values when it is set up (from their trace, below). A model whose value of one instance reads another instance's discrete quantity or memory is not refused: the simulation warns, naming the model, the value, the quantity and the instances, and settles every instance of that model in every round, not only those that switched (correct, slower). An augmentation that integrates sensitivities through the switches also checks it for the rates where several instances switch at one instant (each switch alone from the discrete state before the instant, and each switch left out from the state after it, must change its own instance's rates only) and refuses a kernel that breaks it there; an interaction that shows at neither end remains the kernel author's responsibility.

Tracing the values. Every simulation traces calc_automaton_values! once when it is set up (SparseConnectivityTracer's global detector), for the variables each value reads and for the discrete quantities and memory of each instance, which enter as inputs of their own: the automaton callback then gathers only those variables to compute the values, and an augmentation that locates where a guard grazes a limit reads from the same trace the entries of the state each value reads, the structure its classification of a grazed guard relies on. The time, the variables, the discrete quantities and the memory enter the trace as tracers, so the kernel must not branch on them with if, ?: or &&; an ifelse traces both of its branches, and min, max, abs and arithmetic trace. The real parameters and the setpoints first enter as tracers too, so that the trace holds whatever events do to them; a kernel that branches on them cannot be traced so, and is traced with them at their values, which holds until an event changes them: the trace is made again after a FieldModification or SetpointChange of the model (an event of a kind that does not declare what it changes re-traces every model), and every variable is gathered, whichever the values read. Evaluating the automaton with dual numbers at an instant takes what the values read at their setup, and throws where a later trace finds that it changed. A kernel that cannot be traced either way throws when the simulation is set up, naming the model.

Tracing the residuals. The simulation also traces calc_residuals! when it is set up, for the instances whose discrete quantities or memory a residual without mass reads (an algebraic residual, or the residual of a state whose mass is zero for that instance, as a zero inertia makes it): only their transitions can change the algebraic equations, which the network must then be reinitialized for (PowerFlowInit solves the algebraic variables and the states without mass together). A settle evaluates nothing where none of those switches (an anti-windup automaton, whose gate holds a rate with mass), and otherwise compares the switched models' contributions to the rows without mass before and after the transitions, or the system's rows without mass where a model sets a shared residual (SharedRes(:set), which reads what the others accumulated) or another model sets one where it adds. Here the parameters enter at their values, so a residual kernel may branch on them (a time constant that may be zero); the trace is made again after every event that changes the model's fields (FieldModification; an event of a kind that does not declare what it changes re-traces every model). The variables, the time and the setpoints enter as tracers, so the kernel must not branch on them, nor on the discrete quantities and memory, with if, ?: or &&, and a SetpointChange needs no new trace. Where the algebraic equations changed (a transition, or an event, changed the rows without mass), the reinitialization factorizes its Jacobian afresh, with pivoting, rather than refactorizing with the pivots of an earlier factorization: a mode can move the nonzero of a row off its own variable (REGCA1's high-voltage clamp holds Vt = Volim in the equation of dq), where the old pivot is zero.

Located truths. A value located at its zero (an atom that changed its truth, or a crossing guard) is at zero only to rounding there, and the reinitialization of the network at the instant moves it by the tolerance of its Newton iterations, so the atoms over it are decided by the direction of its motion instead. At the instant, every atom over the value holds as the crossing leaves it (>= and > true after an upward crossing, < and <= false), whichever condition reads it: a release that reads the complement of its hold's atom (hold on x - hi >= 0, release on x - hi < 0) does not fire at the hold. After the instant the value is measured from zero, or from where the instant left it where that is across zero from its side, and a later change of sign is a crossing only where the value's rate points the same way. Otherwise it is what the integration moves the value by besides its motion: a held integrator (its rate gated to zero) still moves by the tolerance of the nonlinear solves, and the short steps after an event move a value by their error, which may be against its rate. Such a value keeps the crossing's truth until the next instant measures it again (held still), or until a step starts with it back on its side (moving back). An automaton that changes mode reads its values afresh. A value whose discrete quantities or memory a transition changes (a timer whose transition records the time it reads) moves by that change, a jump, not by its motion: it loses its side at once, located or not, and is decided by its value, from the same trace of the values (the discrete quantities and memory each reads). A transition located where its value turns back across the surface at once (a Filippov sliding mode) throws, naming the instance.

Rates at located events. The sliding check and the values held at zero by continuity read the rate of a value ġ = g_u u̇ + g_t along the trajectory of the DAE M u̇ = F(u, t). The rate of a value that reads no variable without mass (an algebraic variable, or a state of zero mass) is that of the rows with mass alone, u̇ = F/M, and needs no solve. A value that reads one needs the rows without mass completed, F_ZZ u̇_Z = -(F_ZW u̇_W + ∂F_Z/∂t), which factorizes F_ZZ by KLU (its symbolic analysis kept from one factorization to the next). The check after the transitions takes the factorization from the one before them where no automaton that switched has its discrete state read by a residual without mass and the state and time are the same (the equations of the rows without mass are then those of the event). An F_ZZ that KLU finds singular, or whose condition number it estimates at 1/eps() or more, has no rates: SingularRatesError names its empty rows and columns instead of letting a decision read noise. What the values of a model read is traced once for all the solves of a problem (TDSProblem traces) where the kernel does not branch on parameters or setpoints.

An instant settles in rounds. One rule for every instant (an event while a model runs, the start, the coupling between devices through a network), agreed with the semantic core ("an instant settles in rounds"):

  1. In a round every transition that holds, in every automaton of every in-service instance, fires on the point before the round (_round_steps!). An automaton fires at most one transition per round; two that hold at once from one mode are refused. The sets of the transitions read the values from before the round. No order of automata, modes or transitions means anything.
  2. After the round the algebraic point is solved again from the modes entered, provisionally: the next round reads it. The check is the algebraic check of the settle (AlgebraicRounds, _algebraic_before!, _algebraic_changed!), made for each round on the instances that took a step; a round that leaves the equations without mass as they were leaves the point as it is (it is still a solution), and an instant that settles in one round costs the one solve it always did. The host solves: the phasor simulation by the simulation's initializealg (_reinitialize!), the Y-bus DAE by HostReinit, a fixed-step integration by its own algebraic solve (FixedInstant).
  3. The instant is settled when no transition holds at the point. Only the settled point is published (the integration saves it), and the sliding check and the sides of the located values (_instant_left!) are made there. A nonfinite value, a right side outside its domain, a rate that is not finite or a solve that fails or is singular fails at once, in any round (the integration terminates with ConvergenceFailure, or the error is thrown).
  4. The budget (max_rounds) counts rounds, once for an instance whatever the number of its automata that fire.
  5. The start chooses the initial modes and settles by the same rule. Where the equations without mass in the initial modes do not hold at the point the start was handed (a residual above the integration's tolerance: the initialization does not know which modes the start chooses), the point is solved from them first, then again between the rounds (StartResolve, _settle_rounds!). The adapter starts its automata without a network first (the detection of the state-only constraints reads the discrete state, and the solve needs the constraints), and makes the start again with the solve (_start_automata!) only where that start fired a transition or the equations of the initial modes do not hold at the point; the callback of the integration starts them at its first step with the integration's reinitialization. A start that fires transitions without changing the equations stays at rest (the values decided as zero are not released); one that solves the point is no longer at rest, and releases them.

Values held at zero by continuity. Some values are zero at an instant by the structure of the model, not by a crossing of their own, and their computed value there is rounding of either sign. The generator derives which and writes them into the metadata:

  • Transition(...; continuity = [:surface => [:w, ...]]): where the transition fires on the zero of surface, the values w vanish (in the mode it leaves) and the transition leaves the algebraic state where it is. REGCA1 entering its clamp where Vt crosses Volim holds dq at the zero the clear mode held it at: the clamp's equation, Vt = Volim, already holds there. At the instant the runtime decides the atoms over each w by the sign of w's rate in the mode entered (the rate the sliding check evaluates), and after it measures w as it measures a located value. A rate that points out of the mode fires the next transition at the same instant.
  • Transition(...; crossing_continuity = [:surface => [:w, ...]]): the same, for facts that hold only where the transition fires at a crossing located while the simulation was integrating its source mode, the first round of an instant. The source mode was then settled before the instant, so none of its other exits held. REGCA1's high-voltage clamp (clamp -> clear when dq < 0, clamp -> floor when dq >= 0 and Iq_lag v - dq < Iolim) has Vt - Volim at zero at the release of dq only from a settled clamp: its exit to floor not holding there makes the reactive power of clamp and clear agree. A clamp entered earlier in the same instant has no such guarantee. The runtime decides the values by their rate as with continuity, and never when the transition fires in a later round of the instant, at a start, at an event's reinitialization or at another instant (settle! passes at_crossing, its first round with located, to _held_at_zero!). continuity holds however the source mode was entered.
  • Transition(...; continuity_writers = [:w => [:automaton, ...]]): for a value w held by continuity or crossing_continuity on this transition, the automata of the same instance whose firing voids the hold, because w reads a quantity one of them writes (REECA1's PI clip holds values that read the limit Iqmax, which the automata injection and ipmax_hold can write). The fact the marker states holds for the point as it was before such an automaton fired. The runtime holds w only where none of the listed automata fires in the round of the transition, and decides it by its own value otherwise, as it does a value no marker names (_voided, from the steps of the round). A writer of an earlier round does not void it: the algebraic point is solved again between rounds, and the round of the transition reads what the earlier rounds left (an instant settles in rounds, below). A value not listed has no writers. Powerful refuses a value the transition does not hold, an automaton the model does not have and the transition's own automaton (check_automata). A model declares its writers without regard to the order of its automata: every automaton fires in the round in which its transition holds.
  • A marker of any kind (continuity, crossing_continuity) for a value that reads a quantity the network solves (a variable without mass: a bus voltage, or what a value computes from one) is not applied in a round in which another transition, of any instance, changes a quantity delivered to the network (_moved_through_network): a discrete quantity or memory that a residual without mass reads (a bus_group injection, or a row of the network that a connection reads), set to another number by the mode entered or by a set, or a state the mode entered governs where such a residual reads one (AlgebraicCheck inputs, _delivers_change). The generator derives a marker with the inputs of the model as they are across the transition; what other devices do reaches them through the network, which is Powerful's to bound. REGCA1's LVPL automaton projecting Ip in the round its high-voltage clamp engages moves Pe, so the bus voltage, which the clamp's markers read. The value is then decided by its own value.
  • A rate decides a held value only where the integration resolves its sign (_resolved_rate): |ġ| must exceed the first-order bound Σ_j |∂ġ/∂u_j| tol_j of its error from the state's (tol_j = abstol_j + reltol_j |u_j|; see "The sign of a rate the integration does not resolve" in the TDS architecture page). A rate of the size of that bound is the integration's error (a state oscillating at a rate of the order of 10² per second has a state error of 10⁻⁶ that moves the rate of a slow envelope by about 10⁻⁴), and its sign is a coin. The value then stays at its zero through the instant (zero, kept against the release of an instant that changes the equations, until _instant_left! measures it from where the instant leaves it), so that a transition reading it strictly does not fire on the rounding of the reinitialization, and a crossing that follows is located as any other. The release of REGCA1's clamp (dq crossing zero, which holds Volim - v at zero) is such a value: the measured magnitude is a state continuous across it, so its rate in clear is the clamp's, zero, and the clamp was entered again at once, and left again, to the budget of rounds, at the tolerances where the error was positive. A fixed-step integration has no tolerance and decides by the rate.
  • Automaton(...; at_rest = [:rate, ...]): the rates the initialization makes zero (an anti-windup lag's rate in free, which is zero at the equilibrium the simulation starts from). They are decided as the exact zero they are (>= and <= hold, > and < do not) at the start and while the system stays at that rest. At rest their rates are zero too, so the initial clauses choose, in their order, the mode the model was initialized in: a governor initialized on its (adjusted) valve limit starts and stays in free. The first instant that changes the equations releases them (an event, or a transition anywhere): from there on they are decided by their values.

Conditions that change between the sampled points. The located callback sees a condition change its truth where its component changes sign between two points DiffEq evaluates it at (a step's ends and interp_points between them); a condition that holds only between two of them goes unseen: a value that crosses its surface and comes back inside the step, or atoms that change their truths one after the other (the state reaches its limit, then its rate turns outward). At the start of each step (PowerfulTDS/src/solvers/step_extremum.jl) every component that can fire and has one truth at both ends of the step is examined: where the values its atoms read cross their surfaces inside the step (one crossing where the ends are on different sides; none or two where they are on one, from the extremum of the value on the dense output: the rates at the ends, the derivative of the dense output carried through one Dual evaluation of the values, point opposite ways, the first toward the surface, and the extremum, located by the Hermite of the ends and a Newton step on the rate and shared with the grazing of guards, is beyond it), the truth of the condition between the crossing times follows from the truths of its atoms. Where it differs from that at the start, the component is reported folded (as it is up to a time inside that interval, as its value there after it), a function that changes sign where the condition first changes its truth; DiffEq locates that time, moves the integrator back to it, and the event is that of any other located crossing. An extremum exactly at the surface is a tangency and fires nothing. TDSConfig(locate_extrema = false) leaves such conditions unseen.

Where automata run. The phasor simulation (solve(::TDSProblem)) and the Y-bus simulation (PowerfulYbus) run the automata of their models with the same runtime, and so does any other simulation mode built on TDSProblem: the Y-bus DAE solve locates the transitions with the automaton callback, and the trapezoidal solver cuts its fixed steps where a condition changes its truth (step_automata!), locating the atoms and crossings that changed within the bracket and settling there with the code of the adaptive callback (_located_event!, settle_instant!), the rates of the values that continuity holds at zero evaluated on the Y-bus DAE. A machine model with automata is refused by the Y-bus simulation, whose machine residuals are calc_ybus_residuals!. The Y-bus simulation solves the algebraic rows of the models and the network equations together by one Newton iteration (AlgebraicNewton): REGCA1's g_dq in the clamp, Volim - v, does not read dq, and the Jacobian of the system carries the network's response; a model whose rows do not determine their variables throws, naming the rows and the modes. The events that change a model's data (FieldModification) are applied at their times and the automata trace again what they read (retrace_automata!, the code of the phasor simulation).

Governing a State by a Mode

A mode can hold a differential state on a relation that moves, which a constant hold cannot state: Mode(:upper; holds = [:gate => 0], states = [:y => :upper_bound]) governs y while the model is in upper, the right side being a number or a value the model computes in calc_automaton_values! (a bounded state lowers to such modes: free, upper, lower, pinned, the right side the bound, which may be a parameter, a region's constant or a state that moves). Mode.relations, a branch current's relation, stays refused.

The rate is the model's. In a mode that governs y the residual kernel must give y the rate of its right side, Σ_j (∂r/∂x_j) f_j over the states it reads, gated by what the mode holds (the gate and the bound's rate as discrete quantities); Powerful derives nothing for it. The multistep methods preserve a linear invariant, so the state stays on the relation (y - r = 0 is affine in the states) to the integration's tolerance, as a state-only constraint reduction does (StateConstraintReduction, adapter.jl).

What the right side may read. A governed state is a differential state with mass at every instance, and its right side must be affine in the differential states of its own model with constant coefficients, reading nothing else that evolves. Powerful checks it itself, from the trace of the values (ValueReads) and the degree of each value as a polynomial in the variables and the time (PolyDegree), when the simulation is set up, and again after an event that changes the parameters a branching kernel reads (retrace_automata!):

  • degree at most 1 in the variables and the time, so that its coefficients read no variable (s * w is refused, as is t * s);
  • no algebraic variable, variable without mass or quantity of another model, no time, no discrete quantity or memory (gate * s has a coefficient that evolves);
  • not the governed state itself, and no state governed by any mode of the model (another mode or another automaton): that state moves by its relation, not by its equation;
  • the parameters it reads are finite where the simulation starts (a coefficient that is not finite is refused, naming the right side).

check_automata refuses the declarations that need no trace: a name that is not a differential state of the model, a right side that is not a finite number or a value, and a state governed by the modes of two automata (two modes active together). Each refusal names the model, the mode, the state and the reason. ModelMetadata carries no SemanticModel.invariants (the crossing of moving bounds, x_bounds_ordered): a model that has one is refused by the generator's target before it reaches Powerful.

Entering the mode. The transition that enters a mode writes each state it governs its right side, at that instant (project_states! with the AlongStates policy: the governed state moves, the states the right side reads do not; enforce_state_constraints!, which restores the state-only constraints of a reduced DAE after a fault clears, is the same routine with the MinimumNorm policy over every state of a constraint). A crossing located on x - r lands on the relation only to the located root, so the write is made whether or not it moves the state. After it, inside the same settle: the values that read the state are decided by their values and lose the sides a located crossing gave them (as for a discrete quantity a transition changed); the values are computed again and the guards decided again, so that an immediate release (upper to free) keeps the written state; and an algebraic residual that reads the state (traced with the governed states as inputs of the residuals, or a variable of another model that is the state) ends the round there, so that the network is reinitialized before the next one, as for a mode that changes the algebraic equations. The extremum search of the automaton callback and the continuity of values held at zero take the state after the write: the values are measured from where the instant leaves them (_instant_left!), the held ones decided from their rates in the mode entered, evaluated at the written state (_held_at_zero!). Nothing is written by a trial of the integration: a step the integrator rejects, a root-finding evaluation and the bracketing steps of the fixed-step integration only evaluate the components of the callback; only a settle at an instant, reached through a transition, writes.

Starting. A start refuses a state off its relation, in an initial mode or in a mode the first settle enters, naming the state, the relation and the residual: the right side is computed from the model and cannot be moved to the start, as a computed bound of a VariableLimit cannot (a bound that is a model field is moved by TDSConfig(adjust_limits = true) before the automata are set up, so the right side is read after it).

Two transitions that hold at once from one mode of an automaton are refused (the settle throws, naming both), never ordered by their declaration: the conditions of the transitions from a mode must exclude one another, as the semantic core's reference settle has it. An instance takes part in at most max_rounds rounds at one instant (100 unless the runtime's is set); a round still needed after the budget is spent throws, the count reaching it does not.

When to Use Struct Fields vs External Parameters

Use Struct Fields When:

  • The value is intrinsic to the device (load consumption, generator rating)
  • The value comes from the data file directly
  • It may be modified independently (parameter sweeps, events)
  • It is the same across formulations

Use External Parameters When:

  • The value belongs to another model (bus base kV, bus type)
  • It is derived from topology

Example: PQ loads store their power consumption (intrinsic) but retrieve the bus base voltage (external).

Architecture Integration Points

Address Allocation

setup_with_formulation! reads model_metadata for the problem's formulation. The declarations control address assignments.

Workspace Creation

SystemBuffers uses metadata to create a ResidualBuffers per model. Buffer sizes come from instance counts; buffer fields come from the declarations.

Residual Evaluation

evaluate_system_residuals! calls each model's calc_residuals! in the order given by evaluation_pass.

Automatic Differentiation

Jacobians are computed with ForwardDiff (Dual numbers) or Enzyme through DifferentiationInterface. With ForwardDiff, the workspace buffers hold Dual numbers, so kernels must be generic over the element type.

Per-Unit Conversion

The SystemModel constructor reads the params declarations and converts with bases from ratings and external parameters.

Result Extraction

collect_model_table calls compute_observations. The PUType of each observation selects its conversion to report units.

All integration goes through metadata queries. The core never special-cases model types.

Quick Reference

Minimal Model Template

import PowerfulCore: model_metadata, calc_residuals!, get_terminals, get_key_name

# 1. Struct
@kwdef mutable struct MyModel{Tv} <: AbstractModel
    i::Int32
    id::String3
    status::Bool
    param1::Tv
end

# 2. Registration
@register_model MyModel

# 3. Keys and terminals
get_key_name(::Type{<:MyModel}) = [:i, :id]
const MY_TERMINALS = (Terminal(:Bus, :i),)
get_terminals(::Type{<:MyModel}) = MY_TERMINALS

# 4. Variables
const MY_VARS = [
    ModelVar(:v, AlgebVar(), :Bus, :v, :i; description="Bus voltage magnitude", units="pu"),
]

# 5. Residuals
const MY_RESIDUALS = [
    ModelResidual(:p, AlgebRes(), SharedRes(), :Bus, :p, :i;
                  description="Active power injection"),
]

# 6. Metadata
function model_metadata(::Type{MyModel})
    ModelMetadata(
        name = :MyModel,
        vars = MY_VARS,
        observable_vars = Symbol[],
        residuals = MY_RESIDUALS,
        params = MY_PARAMS,
        ext_params = MY_EXT_PARAMS,
        status_field = :status,
    )
end

# 7. Kernel
@inline function my_kernel!(outputs, params, vars, active, ::Type{<:Vector})
    @inbounds @simd for i in eachindex(outputs.p)
        mask = active[i]
        outputs.p[i] = mask * my_physics(params.param1[i], vars.v[i])
    end
    nothing
end

# 8. Adapter
@inline function calc_residuals!(
    ws::ResidualBuffers{T, AT},
    model::StructArray{<:MyModel},
    _external::NamedTuple,
    ::PowerInjection,
    t = zero(T);
    active_mask::AbstractVector{Bool}
) where {T, AT}
    my_kernel!(
        (p = ws.res_vals.p,),
        (param1 = model.param1,),
        (v = ws.var_vals.v,),
        active_mask,
        AT
    )
end

Follow this pattern and the system handles the rest.
